    Лекция 7: Почему агенты берутся за слишком много и не доделывают

    Краткое введение: Вы говорите Claude Code «добавить аутентификацию пользователей», и он начинает менять схему БД, писать роуты, изменять компоненты фронта и — заодно — рефакторить middleware обработки ошибок. Через два часа: 12 файлов изменено, 800 строк нового кода, и ни одна функция не работает end-to-end.

    Основная идея

    Агенты рождаются с импульсом «сделать чуть больше» — они видят связанное и просто берутся за это. Проблема в том, что делать слишком много вещей одновременно почти гарантирует, что ни одна не будет сделана хорошо. Решение — WIP=1 (Work In Progress = 1): заканчивайте одну задачу, прежде чем начинать следующую.

    Ключевые концепции

    Overreach (Перебор)

    Агент активирует больше задач за сессию, чем оптимально. Это не субъективно — количественно измеримо: делать 5 функций с 0 проходящих end-to-end — это перебор.

    Under-finish (Недоделка)

    Доля задач, проходящих end-to-end верификацию из всех активированных, падает ниже порога. Код написан, но тесты не проходят — это недоделка.

    WIP Limit (Лимит незавершённой работы)

    Из методологии Kanban. Основная идея: ограничить количество одновременно выполняемых задач. Для агентов WIP=1 — самый безопасный вариант по умолчанию.

    Completion Evidence (Доказательство завершения)

    Верифицируемое условие, которое задача должна удовлетворить для перехода из «в процессе» в «выполнено». Без этого агенты подменяют «код выглядит нормально» на «поведение проходит тесты».

    Scope Surface (Поверхность области)

    DAG-структура, где каждый узел — единица работы, а рёбра — зависимости. Состояния ограничены четырьмя: not_started, active, blocked, passing.

    Completion Pressure (Давление завершения)

    Ограничивающая сила, которую harness оказывает через лимиты WIP и требования доказательств завершения, заставляя агента закончить текущую задачу перед началом новой.

    Примеры и эксперименты

    Внимание — конечный ресурс

    Это не метафора — это математика. Пусть ёмкость контекста агента — C, и он активирует k задач одновременно. Каждая задача получает в среднем C/k ресурсов рассуждения. Когда C/k падает ниже минимального порога для завершения одной задачи, ни одна не будет завершена.

    Реальное поведение Claude Code

    Попросите «добавить регистрацию пользователей», и он может: 1. Создать модель User 2. Написать роут регистрации 3. Заметить, что нужна верификация email — добавить почтовый сервис 4. Увидеть, что пароли нужно хешировать — подключить bcrypt 5. Заметить несогласованную обработку ошибок — рефакторить глобальный error-middleware 6. Увидеть, что структура тестовых файлов неаккуратна — реорганизовать директорию

    Шесть шагов спустя — каждый на половине. Нет end-to-end верификации, сложные связи между недоделанным кодом, и следующая сессия будет полностью потеряна.

    Данные Anthropic

    Агенты, использующие стратегию «маленького следующего шага» (эквивалент WIP=1), показывают на 37% более высокую долю завершения задач, чем агенты с широкими промптами. Более интересно: количество строк кода, генерируемых агентами, слабо отрицательно коррелирует с фактическим завершением функций — больше написано кода, меньше функций завершено.

    WIP=1 Workflow

    Очередь функций → Взять ровно одну задачу → Только один активный элемент → Запустить end-to-end верификацию → [прошла] → Коммит и разблокировать следующую задачу
                                                                                                           → [не прошла] → Исправить и повторить

    WIP = 1: Доступный бюджет рассуждения = C. На задачу — C/1. Одна функция достигает состояния «проходит».

    WIP = 5: Доступный бюджет рассуждения = C. На задачу — C/5. Пять частичных реализаций. Низкая доля верифицированного завершения, высокая переделка в следующей сессии.

    Закон Литтла

    L = λ × W. Если незавершённая работа L слишком велика (делаете слишком много одновременно), время выполнения W для каждой задачи不可避免о возрастает. Для агентов это означает, что каждая функция занимает больше времени от старта до верифицированного завершения, и вероятность сбоя растёт.

    Как делать правильно

    1. Принудительно WIP=1. В harness явно скажите агенту: только одна задача может быть в статусе «active» в любой момент.

    ## Правила работы
- Работайте над одной функцией за раз
- Начинайте следующую только после того, как текущая пройдёт end-to-end верификацию
- Не «заодно рефакторьте» функцию B при реализации функции A

    2. Определите явное доказательство завершения для каждой задачи. «Готово» — это не «код написан», а «верификация поведения проходит».

    F01: Регистрация пользователей
  Верификация: curl -X POST /api/register -d '{"email":"test@example.com","password":"123456"}' | jq .status == 201
  Статус: проходит

    3. Экстернализируйте поверхность области. Используйте машиночитаемый файл (JSON или Markdown) для записи всех состояний задач. Любая новая сессия может прочитать и сразу знать: какая задача активна? Какое поведение считается выполненным? Какие верификации прошли?

    4. Мониторьте долю верифицированного завершения (VCR). VCR = верифицированные задачи / активированные задачи. Блокируйте активацию новых задач при VCR < 1.0.

    Реальный случай: REST API проект

    Без ограничений: Агент активировал 5 функций одновременно в сессии 1. ~800 строк в 12 файлах. End-to-end тесты: 20% проходят — только регистрация работает. К концу сессии 3 — только 3 из 8 функций завершены.

    WIP=1: Агент работал только над регистрацией в сессии 1. ~200 строк в 4 файлах. End-to-end тесты: 100% проходят. К концу сессии 4 — 7 из 8 функций завершены (8-я заблокирована внешней зависимостью).

    Результат: меньше общего кода (800 vs 1200 строк), но более эффективный код. Доля завершения: 87.5% vs 37.5%.

    Выводы

    1. WIP=1 — безопасная настройка по умолчанию для harness агентов. Заканчивайте одну, потом начинайте следующую; не пытайтесь параллелить.
    2. Доказательства завершения должны быть исполняемыми. «Код выглядит нормально» не считается; «curl возвращает 201» — считается.
    3. Поверхность области должна быть экстернализирована как файл — не просто упомянута в разговоре, а записана в машиночитаемом формате в репозитории.
    4. Перебор и недоделка — симбиоты. Решение одной проблемы решает другую.
    5. «Делайте меньше, но заканчивайте» всегда побеждает «делайте больше, но оставляйте половину». Количество строк кода агента и доля завершения функций отрицательно коррелируют. Качество всегда побеждает количество.

    Упражнения

    1. Атомизация задач

    Возьмите широкое требование (например, «реализовать систему управления пользователями») и разбейте его на минимум 5 атомарных единиц работы. Для каждой укажите: (а) описание одного поведения, (б) исполняемую команду верификации, (в) зависимости. Проверьте, удовлетворяет ли разбиение ограничению WIP=1.

    2. Сравнительный эксперимент

    Запустите один и тот же проект дважды — один раз без ограничений, другой с принудительным WIP=1. Сравните долю верифицированного завершения, общее количество строк кода и долю эффективного кода.

    3. Аудит доказательств завершения

    Просмотрите вывод недавнего запуска агента, классифицируя каждое изменение кода как «завершённое поведение», «незавершённое поведение» или «каркас». Добавьте недостающие команды верификации для каждого незавершённого поведения.
