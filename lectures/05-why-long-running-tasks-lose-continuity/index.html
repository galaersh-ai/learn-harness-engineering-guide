    Лекция 5: Почему длительные задачи теряют непрерывность

    Краткое введение: Вы просите Claude Code реализовать полную функцию. Он работает 30 минут, делает большую часть работы, но контекст заканчивается. Вы начинаете новую сессию — и обнаруживаете, что агент не помнит принятых решений, почему был выбран вариант A, а не B, какие файлы уже изменены и в каком состоянии тесты.

    Основная идея

    Контекстные окна (context window) конечны. Решение — не в увеличении окон, а в лучшем сохранении состояния. Файлы прогресса, журналы решений и git-чекпоинты работают вместе, позволяя новым сессиям продолжать с того места, где остановились предыдущие.

    Ключевые концепции

    Context Windows Are Finite (Контекстные окна конечны)

    Неважно, какой размер окна заявлен (128K, 200K, 1M) — длительные задачи в конце концов исчерпают их. После исчерпания требуется либо компактизация (потеря информации), либо сброс (новая сессия) — оба варианта что-то теряют.

    State Persistence Files (Файлы сохранения состояния)

    Сохранённые файлы состояния, позволяющие новой сессии однозначно возобновить работу с места остановки предыдущей. Базовая форма включает журналы прогресса, записи верификации и следующие действия.

    Rebuild Cost (Стоимость пересборки)

    Время, необходимое новой сессии для достижения работоспособного состояния. Хороший harness может сократить стоимость пересборки с 15 минут до 3 минут.

    Drift (Дрейф)

    Разрыв между пониманием агента и фактическим состоянием репозитория кода. Каждая граница сессии вносит дрейф; без контроля он накапливается от сессии к сессии.

    Context Anxiety (Контекстная тревожность)

    Феномен, обнаруженный Anthropic — агенты демонстрируют поведение «поспешного завершения» при приближении к лимитам контекста, завершая задачи досрочно для избежания потери информации.

    Compaction vs. Reset (Компактизация vs. Сброс)

    Компактизация суммирует контекст в той же сессии (сохраняет «что», может потерять «why»). Сброс открывает новую сессию, восстанавливая из сохранённых артефактов (чисто, но зависит от полноты артефактов).

    Примеры и эксперименты

    Что происходит при потере непрерывности

    Повторное принятие решений. Предыдущая сессия потратила значительный бюджет контекста на анализ трёх подходов и выбор варианта B. Эта сессия не знает об анализе и может выбрать вариант A.

    Дублирование работы. Агент не уверен, была ли работа выполнена, и делает её снова. Или делает половину, обнаруживает конфликт и переделывает.

    Дрейф направления. За несколько сессий направление реализации может незаметно уйти от исходных требований. Каждая сессия чуть иначе понимает цели проекта.

    Разрыв верификации. Результаты верификации предыдущей сессии не были записаны. Новая сессия заново запускает все проверки.

    Инструменты сохранения состояния

    1. Файл прогресса (PROGRESS.md):

    # Прогресс проекта

## Текущее состояние
- Последний коммит: abc1234 (feat: add user preferences endpoint)
- Статус тестов: 42/43 проходят (test_pagination_edge_case падает)
- Линт: проходит

## Выполнено
- [x] Модель пользователя и миграция БД
- [x] Базовые CRUD-эндпоинты
- [x] Интеграция auth-middleware

## В процессе
- [ ] Функция пагинации (90% — edge case тест падает)

## Известные проблемы
- test_pagination_edge_case возвращает 500 на пустых результатах
- Нужно подтвердить, должны ли удалённые пользователи появляться в списках

## Следующие шаги
1. Исправить баг edge case пагинации
2. Добавить параметр запроса «включить удалённых пользователей»
3. Обновить документацию API

    2. Журнал решений (DECISIONS.md):

    # Архитектурные решения

## 2024-01-15: Использовать Redis для кеширования пользовательских настроек
- Причина: Высокая частота чтения (каждый вызов API), малый объём данных
- Отвергнутая альтернатива: Материализованное представление PostgreSQL (высокая частота изменений делает стоимость обслуживания нецелесообразной)
- Ограничение: TTL кеша 5 минут, активная инвалидация при записи

    3. Git-коммиты как чекпоинты. Коммит после завершения каждой атомарной единицы работы. Сообщения коммитов должны объяснять, что сделано и почему.

    4. init.sh или поток инициализации harness. Укажите в AGENTS.md рутины «прихода на смену» и «ухода со смены».

    Смешанная стратегия

    Не каждой задаче нужен сброс контекста. Короткие задачи (до 30 минут) могут быть выполнены в одной сессии. Длинные задачи (на несколько сессий) должны использовать файлы прогресса и журналы решений. Критерий: если задача требует более 60% окна, начинайте подготовку передачи.

    Глубже о контекстной тревожности

    Anthropic обнаружил: на Sonnet 4.5 при приближении контекста к лимиту агент показывает сильное поведение «поспешного завершения».

    Две стратегии: - Компактизация: Суммирует ранний разговор в той же сессии. Преимущество: непрерывность. Недостаток: «почему» часто теряется. Не устраняет контекстную тревожность. - Сброс контекста: Полная очистка, новая сессия. Преимущество: чистое ментальное состояние. Недостаток: зависит от полноты артефактов передачи.

    Данные Anthropic: для Sonnet 4.5 контекстная тревожность достаточно серьёзна, что компактизации alone недостаточно — сброс контекста становится критическим компонентом. Для Opus 4.5 это поведение значительно减弱.

    Реальный пример: система блога

    Агент должен реализовать систему блога с аутентификацией — 12 функций, ~5 сессий.

    Без сохранения состояния: К сессии 3 накопленный дрейф привёл к пере реализации уже выполненных функций. К сессии 5 — много избыточного кода, но основная функция аутентификации не прошла end-to-end тесты. Выполнено 7 из 12 функций, 3 с скрытыми проблемами.

    С сохранением состояния: Стоимость пересборки сессии 2 — ~3 минуты. К сессии 5 все 12 функций выполнены и верифицированы.

    Количественное сравнение: время пересборки снижено на ~78%, доля выполненных функций — с 58% до 100%, доля скрытых дефектов — с 43% до 8%.

    Выводы

    1. Контекстные окна — конечный ресурс. Длительные задачи будут на несколько сессий, сессии будут терять информацию — это объективная реальность.
    2. Решение — не в больших окнах, а в лучшем сохранении состояния. Файлы прогресса, журналы решений и git-чекпоинты работают вместе.
    3. Treat the agent like an engineer whose short-term memory gets wiped every session: before «clocking out», write down what was done, why, and what's next.
    4. Стоимость пересборки — ключевая метрика. Хороший harness должен выводить новые сессии в работоспособное состояние за 3 минуты.
    5. Смешанная стратегия: короткие задачи в сессии, длинные — со структурированными артефактами для непрерывности.

    Упражнения

    1. Измерение сохранения состояния

    Выберите задачу разработки, требующую не менее 3 сессий. Без файлов сохранения состояния запишите в начале каждой сессии, сколько контекста тратит агент на «разбор того, что было в прошлый раз». После каждой сессии создайте файл прогресса и позвольте следующей начать с него. Сравните стоимости пересборки с файлами и без.

    2. Дизайн шаблона передачи

    Спроектируйте минимальный шаблон передачи с четырьмя полями: состояние репозитория (хеш коммита), состояние выполнения (процент прохождения тестов), блокировщики, следующие действия. Позвольте совершенно свежей сессии восстановить состояние проекта, используя только этот шаблон. Запишите неоднозначности, улучшайте шаблон.

    3. Эксперимент со смешанной стратегией

    В задаче на 5 сессий сравните три стратегии: (а) всегда свежие сессии + файлы прогресса, (б) максимум в одной сессии (компактизация контекста), (в) смешанная (короткие в сессии, длинные через сессии + файлы прогресса). Сравните время пересборки, долю выполненных функций и согласованность решений.
