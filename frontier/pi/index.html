    Разбор дизайна харнеса Pi

    Pi (npm-пакет @earendil-works/pi-coding-agent) описывает себя как «минимальный харнес агента». Эта фраза стоит распаковать: он не называет себя «самым мощным агентом для кодирования» или «лучшим инструментом AI-программирования». Вместо этого он прочно закрепляет свою идентичность в слове харнес.

    В этой статье мы используем фреймворк пяти подсистем курса — инструкции, инструменты, среда, состояние и обратная связь — для изучения Pi и определения того, как его философия дизайна фундаментально отличается от Claude Code и Codex. Вот ответ заранее: философия Pi — «минимизировать ядро + сделать расширения программируемыми». Она выводит инженерию контекста за пределы системного промпта и позволяет пользователям — даже самому Pi — модифицировать харнес, вместо того чтобы Pi решал харнес за вас.

    В одном предложении

    Pi — это минимальное ядро: его официальная позиция намеренно сохраняет ядро малым и возвращает контроль вам. По словам домашней страницы pi.dev, «Попросите Pi построить то, что вы хотите, или установите пакет, который сделает это по-вашему». Он разделяет харнес на четыре настраиваемых слоя:

    • Расширения: TypeScript-хуки, прикреплённые к событиям жизненного цикла Pi, обеспечивающие программируемую поверхность на уровне среды выполнения.
    • Навыки: Пакеты возможностей по запросу, содержащие инструкции и инструменты, использующие прогрессивное раскрытие.
    • Шаблоны промптов: Многоразовые Markdown-промпты, которые расширяются при вводе /name.
    • Темы: Внешний вид TUI.

    Этот многослойный подход сам по себе является формой дизайна харнеса: правила и расширения полностью определяют, что модель может видеть и когда она может это видеть, вместо того чтобы эти решения были жёстко закодированы в ядре.

    Основной цикл

    Как и каждый агент для кодирования, Pi в основе представляет собой while-цикл «рассуждение → выполнение инструмента → наблюдение → дальнейшие рассуждения». Важен не сам цикл, а то, как Pi обрабатывает слой вокруг него: он расширяет управление контекстом от «сжатия» внутри цикла до «управления» снаружи цикла.

    Среда выполнения Pi предоставляет программируемый интерфейс. В дополнение к интерактивному TUI, раздел Programmatic Usage исходного README поддерживает скриптовые режимы print/JSON, протокол RPC и встраивание SDK. Это означает, что один и тот же харнес может управляться пошагово человеком или автоматически CI/CD или другой программой. Это обеспечивает предпосылку для перехода «от ручного управления к автоматизированным циклам», описанного в Лекции 13 об инженерии циклов: харнес, который может управляться только интерактивно человеком, никогда не войдёт в автоматизированный цикл.

    Подсистема инструкций: AGENTS.md и SYSTEM.md

    Pi сдержан в обработке инструкций, но его иерархия чёткая:

    • AGENTS.md: раздел Project Context Files исходного README явно документирует порядок загрузки: глобальный ~/.pi/agent/AGENTS.md → обход родительских каталогов вверх уровень за уровнем → ./AGENTS.md в текущем каталоге (с совместимостью CLAUDE.md). Это воплощает «репозиторий как систему записи» на практике — инструкции являются файлами, а не напоминаниями, набранными в чате.

    • SYSTEM.md: официальная документация pi.dev говорит, что системный промпт по умолчанию может быть заменён или дополнен для каждого проекта. Это единственный официальный вход Pi для модификации «системного промпта» и также служит его слоем «самоописания среды».

    Pi официально подчёркивает, что его системный промпт минимален. Это отражает явный компромисс: ядро не набивает длинные списки правил «если...то...». Вместо этого оно предоставляет точки расширения, чтобы правила появлялись как навыки и расширения только тогда, когда они нужны. Это непосредственно перекликается с Лекцией 4, «Почему один гигантский файл инструкций терпит неудачу» — Pi естественным образом избегает проблемы гигантского файла инструкций через подход «минимальное ядро + разделённые файлы + загрузка по запросу».

    Состояние и контекст: где Pi наиболее детален

    Инженерия контекста Pi заслуживает особого внимания, потому что она превращает концепции курса, такие как «преемственность контекста» и «предотвращение загрязнения контекста», в конкретные механизмы:

    1. Программируемое сжатие. По мере приближения к пределу контекста старые сообщения автоматически суммаризируются. Официальная документация pi.dev объясняет, что стратегия сжатия сама по себе настраиваема: вы можете использовать расширения для реализации сжатия на основе тем, суммаризаций, учитывающих код, или даже использовать другую модель для суммаризации. Исходный README также раскрывает детали механизма по умолчанию: автоматическое сжатие запускается в двух случаях (восстановление после переполнения контекста / превышение порога удержания), точка разделения сохраняет приблизительно последние 20 000 токенов, а более ранние сообщения суммаризируются в «передачу контекста» и сжимаются инкрементально в цепочке. Другими словами, Pi рассматривает «как сжимать» не как фиксированную константу, а как часть харнеса.

    2. Динамический контекст. Официальная документация pi.dev говорит, что расширения могут вводить сообщения перед каждым ходом рассуждения, фильтровать историю сообщений, реализовывать RAG и строить долгосрочную память. Это выходит за рамки «сжимать, когда контекст полон»: это позволяет вам решать, что входит в окно контекста до того, как оно туда попадёт. С точки зрения целей курса «сделать выполнение агента наблюдаемым и отлаживаемым» и «поддерживать преемственность контекста», Pi продвигает оба вниз к поверхности расширений.

    3. Дерево сессий. Домашняя страница pi.dev явно говорит «сессии хранятся как деревья»; /tree может вернуться к любому историческому узлу и продолжить оттуда, при этом каждая ветвь хранится в том же файле. Это решает разрывы контекста между сессиями, многократно подчёркиваемые в курсе — не путём принуждения суммаризаций заполнять разрыв, а через структурированное воспроизведение истории. Ветви могут быть экспортированы как HTML или загружены как gist для обмена, что также обеспечивает наблюдаемость.

    Подсистема инструментов: навыки и расширения

    «Инструменты» Pi имеют два слоя:

    • Навыки: раздел Skills исходного README определяет их как «автономные пакеты возможностей, которые агент загружает по запросу». Они содержат инструкции и инструменты и следуют стандарту Agent Skills. Прогрессивное раскрытие гарантирует, что детали навыков входят в контекст только при активации, не переполняя кэш промптов. Это дизайн харнеса с точки зрения стоимости: каждый дополнительный токен в контексте должен быть оплачен при каждом выводе. Загрузка навыков по запросу — это ещё одно выражение «дать карту, а не руководство».

    • Расширения: TypeScript-хуки, прикреплённые к встроенным событиям жизненного цикла. Раздел Hooks исходного README даёт официальные примеры: перехват опасных команд (шлюз разрешений), создание контрольных точек состояния кода при переключении задач, защита путей (например, запрет записи в .env), модификация вывода инструмента перед передачей модели и ввод сообщений из внешних источников (наблюдатели за файлами/Webhooks/CI) для пробуждения агента. Эти API хуков также экспортируются из @mariozechner/pi-coding-agent/hooks. Сообщество харнес pi-agent-harness дополнительно упаковывает эту поверхность хуков в готовые расширения, такие как skill-router, session-summary, extract-patterns и telemetry.

    Расширения — это самое важное дизайнерское решение Pi: вместо того чтобы просто дать пользователям несколько переключателей, Pi предоставляет всю поверхность событий внутри среды выполнения. Хотите добавить память? Введите на agent/pre-step. Хотите записать поведение? Подпишитесь на события сессии. Хотите изменить запрос модели? Подключитесь к agent/request. Вы можете заставить Pi модифицировать свой собственный харнес — это ближе к определению «программируемого харнеса», чем любой набор параметров конфигурации.

    Обратная связь и верификация: превращение «обучения» в часть харнеса

    Сам Pi не включает обязательных тестовых ворот (пользователи должны указать команды верификации в AGENTS.md), но сообщество харнес pi-agent-harness использует расширения для структурирования «цикла обратной связи». Раздел Hooks официального README обеспечивает основу для аналогичных механизмов:

    • session-summary (расширение pi-agent-harness): Поддерживает скользящие записи PROGRESS.md — подсистема состояния курса, используемая для отслеживания прогресса в долгосрочных задачах.
    • extract-patterns (расширение pi-agent-harness): Собирает кандидатские уроки из сессий и записывает их в LESSONS.md — превращение «оставить хорошую передачу перед завершением каждой сессии» из соглашения в механизм.
    • telemetry (расширение pi-agent-harness): Записывает использование токенов, стоимость и связанные метрики — наблюдаемость.

    Тот же репозиторий сообщества further демонстрирует паттерн: VISION.md (цели), PROGRESS.md (прогресс), LESSONS.md (уроки) и STANDARDS.md (стандарты) — все Markdown-файлы, сохраняемые между сессиями. Это exactly паттерн «репозиторий как система записи + файлы прогресса + механизм передачи», рекомендуемый курсом, доступный из коробки через механизм расширений Pi.

    Соответствие фреймворку курса

    Оценка Pi по пяти подсистемам курса (субъективно, для сравнения):

    Подсистема Реализация Pi Оценка
    Инструкции Иерархическая загрузка AGENTS.md + SYSTEM.md Чёткая иерархия, но пользователи должны писать правила сами
    Инструменты Навыки по запросу + хуки полного жизненного цикла расширений Extremely strong; превращает систему инструментов в программируемую поверхность
    Среда SYSTEM.md для самоописания среды; пользователи объявляют среду выполнения в AGENTS.md Механизм открыт, но воспроизводимость зависит от описаний, написанных пользователями
    Состояние Дерево сессий + настраиваемое сжатие + PROGRESS.md Extremely strong; преемственность между сессиями и восстанавливаемость — центральные
    Обратная связь Пользовательские команды верификации; структурированные механизмы session-summary / extract-patterns Механизм предоставлен; пользователи поставляют содержимое

    Компромиссы Pi резко контрастируют с Claude Code и Codex. Claude Code помещает «память, разрешения и субагентов» в ядро для готового к использованию опыта; Codex делает «соглашения репозитория и изоляцию среды» значениями по умолчанию. Pi выбирает ничего не решать за вас — он превращает решения в точки расширения. Стоимость в том, что вы должны либо писать расширения сами, либо устанавливать пакеты, написанные другими.

    Дизайны, которые стоит перенять

    1. Сделайте стратегию сжатия подключаемой. «Как контекст сжимается» в вашем харнесе не должно быть жёстко закодированным параметром; это должен быть заменяемый интерфейс стратегии.
    2. Используйте дерево сессий вместо принудительных суммаризаций. Восстановление между сессиями не обязательно должно полагаться на «суммаризацию предыдущего хода»; структурированное воспроизведение истории часто является более надёжной подсистемой состояния.
    3. Будьте дружелюбны к кэшу промптов. Загружайте навыки по запросу, а не помещайте каждое правило в системный промпт сразу. Это и инженерия контекста, и инженерия стоимости.
    4. Позвольте агенту модифицировать свой собственный харнес. Если харнес предоставляет достаточно точек расширения, оптимизация поведения агента itself может быть частично автоматизирована агентом.

    Ссылки (оригинальные источники / исходный код)

    Каждое утверждение можно проследить до оригинальных источников или исходного кода ниже, избегая пересказов:

    • pi.dev: Оригинальная позиция, «Попросите Pi построить то, что вы хотите, или установите пакет, который сделает это по-вашему»; четыре настраиваемых слоя; и деревья сессий («сессии хранятся как деревья», /tree, хранение в одном файле, экспорт HTML / обмен gist). https://pi.dev/
    • pi.dev · Sessions: Подключаемое сжатие (на основе тем / учитывающее код / альтернативная модель суммаризации), автоматическое сжатие и механизмы ввода динамического контекста. https://pi.dev/docs/usage/sessions
    • pi.dev · Extensions: Расширения могут вводить сообщения перед каждым ходом рассуждения, фильтровать историю, выполнять RAG и строить долгосрочную память. https://pi.dev/docs/usage/extensions
    • pi.dev · Project Context: Семантика замены / дополнения SYSTEM.md. https://pi.dev/docs/usage/project-context
    • Pi Coding Agent README (badlogic/pi-mono): Трёхуровневый порядок загрузки AGENTS.md (глобальный → родительские каталоги → текущий каталог), /compact и условия запуска и точка разделения 20 000 токенов для автоматического сжатия, навыки по запросу и стандарт Agent Skills, жизненный цикл Hooks и четыре официальных примера использования, и Programmatic Usage (JSON / RPC / SDK). https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md
    • pi-agent-harness: Расширения skill-router / session-summary / extract-patterns / telemetry и файловая система VISION.md / PROGRESS.md / LESSONS.md / STANDARDS.md. https://github.com/LabidySabidy/pi-agent-harness
