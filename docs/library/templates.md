# Руководство по шаблонам

Эти шаблоны готовы к копированию в ваш проект. Каждый из них служит определённой цели в рабочем процессе агента. Редактируйте содержимое в соответствии с командами, путями, именами функций и шагами верификации вашего проекта.

## Как начать

Скопируйте эти четыре файла в корень вашего проекта:

1. `AGENTS.md` или `CLAUDE.md`
2. `init.sh`
3. `claude-progress.md`
4. `feature_list.json`

Добавьте остальные файлы по мере роста вашего проекта.

---

## AGENTS.md

Корневой файл инструкций. Это первое, что читает агент при запуске сессии. Он определяет правила работы: что делать перед написанием кода, как работать и как завершать работу.

**Как использовать:**

- Скопируйте в корневой каталог вашего проекта
- Замените шаги рабочего процесса запуска на реальные пути и команды вашего проекта
- Настройте правила работы в соответствии с соглашениями вашей команды
- Сохраните раздел «definition of done» — это самая важная часть

**Что он делает для агента:**

- Говорит ему прочитать прогресс и состояние функций перед началом работы
- Заставляет работать над одной функцией за раз
- Требует доказательства перед пометкой чего-либо как выполненного
- Определяет, как выглядит чистое завершение сессии

Используйте `AGENTS.md` для Codex или других агентов. Используйте `CLAUDE.md`, если вы работаете с Claude Code — структура та же, просто отформатирована для стиля инструкций Claude.

## init.sh

Скрипт запуска. Выполняет установку зависимостей, верификацию и выводит команду запуска — всё за один раз.

**Как использовать:**

- Скопируйте в корень проекта
- Отредактируйте эти три переменные вверху:
    - `INSTALL_CMD` — команда установки зависимостей (например, `npm install`, `pip install -r requirements.txt`)
    - `VERIFY_CMD` — базовая команда верификации (например, `npm test`, `pytest`)
    - `START_CMD` — команда запуска dev-сервера (например, `npm run dev`)
- Сделайте его исполняемым: `chmod +x init.sh`

**Что он делает:**

1. Выводит текущий каталог (чтобы вы могли убедиться, что он запускается в правильном месте)
2. Устанавливает зависимости
3. Запускает команду верификации
4. Выводит команду запуска (или запускает её, если установлена `RUN_START_COMMAND=1`)

Если верификация fails, агент должен остановиться и исправить базовую линию перед тем, как делать что-либо ещё.

## claude-progress.md

Журнал прогресса. Каждая сессия пишет в этот файл, и каждая новая сессия читает его первой.

**Как использовать:**

- Скопируйте в корень проекта
- Заполните раздел «Current Verified State» информацией о вашем проекте
- После каждой сессии обновляйте запись сессии

**Что означает каждое поле:**

- **Current Verified State** — единый источник правды о текущем состоянии проекта
    - `Repository root directory` — где живёт проект
    - `Standard startup path` — команда для запуска проекта
    - `Standard verification path` — команда для запуска тестов
    - `Highest priority unfinished feature` — над чем должна работать следующая сессия
    - `Current blocker` — всё, что застряло
- **Session Record** — одна запись на сессию
    - `Goal` — что планировалось сделать
    - `Completed` — что было фактически сделано
    - `Verification run` — какие тесты были выполнены
    - `Evidence recorded` — какие доказательства были зафиксированы
    - `Commits` — что было закоммичено
    - `Known risks` — что может быть сломано
    - `Next best action` — с чего должна начать следующая сессия

## feature_list.json

Трекер функций. Машиночитаемый список всех функций, которые агент должен реализовать, вместе с их статусом, шагами верификации и доказательствами.

**Как использовать:**

- Скопируйте в корень проекта
- Замените примеры функций на свои собственные
- Каждая функция требует:
    - `id` — короткий уникальный идентификатор
    - `priority` — целое число, меньше = выше приоритет
    - `area` — какая часть приложения (например, «chat», «import», «search»)
    - `title` — краткое описание
    - `user_visible_behavior` — что должен видеть пользователь, когда это работает
    - `status` — одно из: `not_started`, `in_progress`, `blocked`, `passing`
    - `verification` — пошаговые инструкции для подтверждения работоспособности
    - `evidence` — зафиксированное доказательство прохождения верификации (заполняется агентом)
    - `notes` — любой дополнительный контекст

**Правила статуса:**

- `not_started` — не тронуто
- `in_progress` — одна функция, над которой в данный момент работает (только одна за раз)
- `blocked` — невозможно продолжить из-за задокументированной проблемы
- `passing` — верификация пройдена и доказательства зафиксированы

Агент должен иметь только одну функцию в статусе `in_progress` в любой момент времени.

## session-handoff.md

Компактная записка передачи между сессиями. Используйте её, когда сессия заканчивается и вы хотите, чтобы следующая быстро подхватила работу.

**Как использовать:**

- Скопируйте в корень проекта
- Заполняйте в конце каждой сессии (или пусть агент заполняет)

**Что охватывает каждый раздел:**

- **Currently verified** — что подтверждено как работающее и какая верификация была запущена
- **Changes this session** — какой код или инфраструктура изменились
- **Still broken or unverified** — известные проблемы и рискованные области
- **Next best action** — что должна делать следующая сессия и чего не трогать
- **Commands** — команды запуска, верификации и отладки для быстрого доступа

Этот файл необязателен для небольших сессий. Он становится важным, когда сессии длинные или когда проект имеет несколько активных областей.

## clean-state-checklist.md

Чеклист для проверки перед завершением каждой сессии. Убеждается, что репозиторий находится в хорошем состоянии для чистого начала следующей сессии.

**Как использовать:**

- Скопируйте в корень проекта
- Пройдите по нему перед закрытием сессии
- Агент также должен проверять эти пункты как часть своей процедуры завершения сессии

**Что он проверяет:**

- Стандартный запуск всё ещё работает
- Стандартная верификация всё ещё запускается
- Журнал прогресса обновлён
- Список функций отражает фактическое состояние (нет ложных записей `passing`)
- Нет незавершённой работы, оставленной без записи
- Следующая сессия может продолжить без ручных исправлений

## evaluator-rubric.md

Карта оценки для проверки качества вывода агента. Используйте её после сессии или на вехах проекта, чтобы оценить, соответствует ли работа требованиям.

**Как использовать:**

- Скопируйте в корень проекта
- После сессии (или набора сессий) оцените работу агента по шести измерениям
- Каждое измерение оценивается от 0 до 2

**Шесть измерений:**

1. **Correctness** — соответствует ли реализация целевому поведению?
2. **Verification** — были ли запущены необходимые проверки с доказательствами?
3. **Scope discipline** — остался ли агент в рамках выбранной функции?
4. **Reliability** — переживёт ли результат перезапуск или повторный запуск?
5. **Maintainability** — достаточно ли код и документация понятны для следующей сессии?
6. **Handoff readiness** — может ли новая сессия продолжить, используя только артефакты репозитория?

**Варианты заключения:**

- Accept — соответствует требованиям
- Revise — нужны исправления перед принятием
- Block — фундаментальные проблемы, которые нужно решить

**Важно: оценщик нуждается в настройке.** По умолчанию агенты плохо оценивают сами себя — они находят проблемы, а затем убеждают себя в обратном. Вам придётся итерировать:

1. Запустите оценщика на завершённом спринте.
2. Сравните его оценки с вашим собственным человеческим суждением.
3. Там, где они расходятся, сделайте рубрику более конкретной по критериям прохождения/провала.
4. Повторно запустите и проверьте совпадение.
5. Повторяйте, пока оценщик не будет последовательно совпадать с человеческой проверкой.

Планируйте 3-5 раундов настройки. Записывайте каждое изменение, чтобы отслеживать, что улучшило совпадение.

## quality-document.md

Снимок качества, который оценивает каждый продуктовый домен и архитектурный слой в вашем проекте. Отслеживает здоровье кодовой базы с течением времени, а не только вывод отдельной сессии.

**Как использовать:**

- Скопируйте в корень проекта
- Перед началом сессии: прочитайте, чтобы понять, где кодовая база наиболее слаба
- После сессии: обновите оценки на основе того, что изменилось
- Со временем: сравнивайте снимки, чтобы увидеть, какие изменения харнеса действительно улучшили здоровье кодовой базы

**Что оценивается:**

- **Продуктовые домены** (например, импорт документов, поток Q&A, индексация): каждый домен получает оценку (A-D) по статусу верификации, читаемости для агента, стабильности тестов и ключевым пробелам
- **Архитектурные слои** (например, основной процесс, preload, renderer, services): каждый слой получает оценку за соблюдение границ и читаемость для агента

**Почему это важно:**

Рубрика оценщика оценивает отдельные выводы агента. Документ качества оценивает саму кодовую базу. Они отвечают на разные вопросы:

- Рубрика оценщика: «Хорошо ли агент поработал в этой сессии?»
- Документ качества: «Становится ли проект сильнее или слабее со временем?»

**Когда обновлять:**

- После каждой значительной сессии
- Перед сравнениями бенчмарков
- После проходов по очистке или упрощению
- При подключении нового агента или модели к проекту

**Связь с упрощением харнеса:**

Документ качества также поддерживает упрощение харнеса. Каждый компонент харнеса кодирует предположение о том, что модель не может делать. По мере улучшения моделей эти предположения устаревают. Чтобы проверить, нужен ли ещё компонент:

1. Сделайте снимок документа качества.
2. Удалите один компонент харнеса.
3. Запустите набор бенчмарковых задач.
4. Сделайте ещё один снимок.
5. Сравните — если оценки не упали, компонент был накладными расходами. Если упали — восстановите его.
