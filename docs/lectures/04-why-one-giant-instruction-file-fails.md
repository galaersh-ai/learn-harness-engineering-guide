# Лекция 4: Почему один гигантский файл инструкций не работает

Краткое введение: Вы создали AGENTS.md и впихнули туда каждое правило, ограничение и урок. Через месяц файл раздулся до 300 строк, через два — до 450, через три — до 600. И производительность агента стала... хуже. Это ловушка «гигантского файла инструкций».

## Основная идея

«Добавить правило» каждый раз, когда что-то идёт не так — естественная реакция, но кумулятивный эффект катастрофичен. Решение — разбиение инструкций на файлы с принципом «показывать по требованию» (reveal on demand).

## Ключевые концепции

### Instruction Bloat (Раздувание инструкций)
Когда файл инструкций занимает 10–15% контекстного окна (context window), он начинает вытеснять бюджет на чтение кода и рассуждения о задаче. 600-строчный AGENTS.md может потреблять 10 000–20 000 токенов — это 8–15% окна в 128K.

### Lost in the Middle (Потерянность в середине)
Исследование Liu et al. (2023) показало, что LLM значительно хуже используют информацию в середине длинных текстов, чем в начале или конце. Критическое ограничение, зарытое на строке 300 из 600, с высокой вероятностью будет проигнорировано.

### Instruction SNR (Signal-to-Noise Ratio)
Доля инструкций в файле, релевантных текущей задаче. Если во время исправления бага вынуждены читать 50 строк инструкций по деплою — это низкое соотношение сигнала к шуму.

### Entry File (Файл входа)
Короткий файл-точка входа, цель которого — направить агента к более подробной документации, а не содержать всё самому. 50–200 строк достаточно.

### Reveal on Demand (Показывать по требованию)
Сначала обзорная информация, подробности — по мере необходимости. Хороший дизайн harness как хороший UI — не вываливайте все опции на пользователя сразу.

### Can't Tell What Matters (Непонятно, что важно)
Когда все инструкции выглядят одинаково, агент не может отличить абсолютные красные линии от мягких рекомендаций.

## Примеры и эксперименты

### Порочный цикл

1. Агент делает ошибку
2. Вы говорите «добавить правило»
3. Добавляете в AGENTS.md — работает (временно)
4. Агент делает другую ошибку
5. Добавляете ещё правило
6. Повторяйте, пока файл не раздуется

### Что именно идёт не так

**Бюджет контекста съедается.** Окно контекста конечно. Сложная задача может потребовать чтения десятков исходных файлов, вывод инструментов тоже занимает контекст, история разговора накапливается.

**Потерянность в середине.** AGENTS.md из 600 строк, строка 300 — «все запросы к БД должны использовать параметризованные запросы». Это ограничение безопасности, но оно зарыто в середине и будет проигнорировано.

**Конфликты приоритетов.** Файл смешивает абсолютные ограничения («никогда не используйте eval()»), важные рекомендации («предпочитайте функциональный стиль») и конкретный исторический урок. Агент не имеет надёжного сигнала для различения.

**Разложение обслуживания.** Большие файлы inherently трудны для поддержки. Устаревшие инструкции редко удаляются, новые добавляются бесплатно. Файл только растёт.

**Накопление противоречий.** Инструкции, добавленные в разное время, начинают противоречить друг другу.

### Реальный пример: SaaS-команда

AGENTS.md раздулся с 50 до 600 строк. Смешались версии стека, стандарты кодирования, исторические заметки об исправлении багов, руководства по API, процедуры деплоя и личные предпочтения членов команды.

**После рефакторинга:**
- AGENTS.md сокращён до 80 строк: только обзор, команды запуска и 15 глобальных жёстких ограничений
- Созданы тематические документы: `docs/api-patterns.md` (120 строк), `docs/database-rules.md` (60 строк), `docs/testing-standards.md` (80 строк)
- Добавлены ссылки на тематические документы в файле входа
- Исторические заметки либо преобразованы в тесты, либо удалены

**Результат:** успешность на том же наборе задач выросла с 45% до 72%. Соблюдение ограничений безопасности — с 60% до 95%.

### Код: пример файла входа AGENTS.md

```markdown
# AGENTS.md

## Обзор проекта
Python 3.11 FastAPI backend, PostgreSQL 15 database.

## Быстрый старт
- Установка: `make setup`
- Тесты: `make test`
- Полная проверка: `make check`

## Жёсткие ограничения
- Все API должны использовать OAuth 2.0 аутентификацию
- Все запросы к БД должны использовать SQLAlchemy 2.0
- Все PR должны проходить pytest + mypy --strict + ruff check

## Тематические документы
- Паттерны API (`docs/api-patterns.md`) — Обязательно при добавлении эндпоинтов
- Правила БД (`docs/database-rules.md`) — При изменении операций с БД
- Стандарты тестирования (`docs/testing-standards.md`) — Справка при написании тестов
```

## Выводы

1. «Добавить правило» — краткосрочное облегчение и долгосрочный яд. Перед добавлением правила подумайте, не лучше ли оно в тематическом документе.
2. Файл входа — это маршрутизатор, а не энциклопедия. 50–200 строк — обзор, жёсткие ограничения и только ссылки.
3. Используйте эффект «потерянности в середине»: важную информацию — в начало или конец, менее критичную — в тематические документы.
4. Управляйте раздуванием инструкций так же, как техническим долгом. Регулярный аудит, каждая инструкция должна иметь источник, условие применимости и условие истечения.
5. После разбиения SNR улучшается, и агент тратит больше бюджета контекста на саму задачу.

## Упражнения

### 1. Аудит SNR
Возьмите ваш текущий файл инструкций и перечислите все записи. Выберите 5 различных типичных задач и отметьте, релевантна ли каждая инструкция для этой задачи. Вычислите SNR для каждого типа задачи. Инструкции, являющиеся шумом для большинства задач, следует переместить в тематические документы.

### 2. Рефакторинг «показывать по требованию»
Если у вас файл инструкций более 300 строк, разделите его на: (а) файл входа менее 100 строк, (б) 3–5 тематических документов. Запустите один и тот же набор задач (не менее 5) до и после рефакторинга и сравните успешность.

### 3. Проверка «потерянности в середине»
В длинном файле инструкций разместите критическое ограничение в начале, середине и конце соответственно, запуская один и тот же набор задач каждый раз (не менее 5 запусков на позицию). Посмотрите, есть ли разница в частоте соблюдения.
