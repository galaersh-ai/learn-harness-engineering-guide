# Лекция 9: Почему списки функций являются примитивами харнеса

## Введение

Вы просите агента создать сайт электронной коммерции. После завершения он сообщает «готово». Вы смотрите на код — аутентификация пользователя работает, но кнопка оформления заказа в корзине ничего не делает, а платёжный процесс вообще не подключён. Что пошло не так? Вы никогда не объяснили ему, что значит «готово», поэтому он использовал собственный стандарт: «Я написал много кода, и он выглядит довольно полным».

Списки функций в глазах многих — просто записка: запишите, чтобы не забыть, а потом отложите в сторону. Но в мире харнесов список функций — это не записка для людей. Это фундаментальная структура, на которой строится весь харнес. Планировщик依赖 от него для выбора задач, верификатор — для оценки завершённости, а отчёт о передаче — для генерации сводок. Без него у этих компонентов нет общей основы для работы.

Anthropic и OpenAI подчёркивают: **артефакты должны быть внешнизированы**. Состояние функций должно храниться в машиночитаемом файле в репозитории, а не в неструктурированном тексте разговора.

## Основная идея

Агенты не знают, что значит «готово». Ни Claude Code, ни Codex автоматически не понимают, что вы имеете в виду. Вы говорите «добавь функцию корзины», а модель интерпретирует это как «напиши компонент Cart и метод addToCart». Но вы имели в виду «пользователь может просматривать товары, добавлять в корзину и завершать оформление заказа от начала до конца».

Без списка функций этот разрыв в понимании сохраняется. Агент использует собственный неявный стандарт — обычно «в коде нет очевидных синтаксических ошибок». А вам нужна поведенческая верификация от начала до конца.

## Ключевые концепции

- **Списки функций — примитивы харнеса**: Не «опциональные инструменты планирования», а фундаментальные структуры данных, от которых зависят все остальные компоненты харнеса. Планировщик, верификатор и отчёт о передаче — все нуждаются в чтении списка функций для работы.

- **Тройная структура**: Каждый элемент функции содержит три элемента: `(описание поведения, команда верификации, текущее состояние)`. Поведение говорит агенту, что делать, верификация — что считается завершённым, а состояние — где всё находится. Отсутствие любого элемента делает запись неполной.

- **Модель конечного автомата**: Каждый элемент функции имеет четыре состояния — `not_started`, `active`, `blocked`, `passing`. Переходы состояний контролируются харнесом, а не свободно изменяются агентом.

- **Ворота состояния прохождения**: Единственный способ перевести функцию из `active` в `passing` — успешное выполнение команды верификации. Этот переход необратим —一旦 `passing`, обратного пути нет.

- **Единый источник истины**: Вся информация о «что нужно сделать» должна происходить из одного списка функций. Никаких противоречий между списком функций и историей разговора.

- **Обратное давление**: Количество функций, которые ещё не прошли проверку, — это давление, которое харнес оказывает на агента. Нулевое давление = проект завершён.

## Примеры

### Режим записок (неструктурированный)
Агент использует неструктурированные заметки для отслеживания прогресса. После 3 сессий заметки становятся: «сделал аутентификацию и список товаров, корзина почти готова, но есть баги, оплата не начата». Новой сессии требуется 20 минут, чтобы вывести состояние проекта, и в итоге она повторно реализует уже завершённые функции.

### Структурированный режим
Каждая функция имеет чёткое состояние и команду верификации. Новая сессия читает список функций и за 3 минуты понимает: F01-F05 в состоянии `passing`, F06 `active` (в процессе), F07-F10 `not_started`. Она продолжает работу с F06 без переделки.

**Количественный результат**: проекты со структурированными списками функций показывают на 45% более высокий процент завершения функций по сравнению со свободным отслеживанием, без повторных реализаций.

### Формат списка функций (JSON)

```json
{
  "id": "F03",
  "behavior": "POST /cart/items with {product_id, quantity} returns 201",
  "verification": "curl -X POST http://localhost:3000/api/cart/items -H 'Content-Type: application/json' -d '{\"product_id\":1,\"quantity\":2}' | jq .status == 201",
  "state": "passing",
  "evidence": "commit abc123, test output log"
}
```

### Правила в CLAUDE.md

```
## Feature List Rules
- Feature list file: /docs/features.md
- Only one feature active at a time
- Verification command must pass before marking as passing
- Don't modify feature list states yourself — the verification script updates them automatically
```

## Выводы

- Списки функций — фундаментальная структура харнеса, а не записки для людей. Планировщик, верификатор и отчёт о передаче зависят от них.
- Каждый элемент функции должен содержать тройку: описание поведения + команда верификации + текущее состояние. Отсутствие одного элемента делает запись неполной.
- Переходы состояний контролируются харнесом — агент не может менять состояния сам. Прохождение верификации — единственный путь повышения.
- Список функций — единственный источник истины проекта. Вся информация о «что делать» происходит из него.
- Калибруйте гранулярность на «завершаемое за одну сессию». Слишком широко — не завершится, слишком узко — невозможно управлять.

## Упражнения

1. **Проектирование списка функций**: Определите минимальную JSON-схему списка функций. Включите: id, описание поведения, команду верификации, текущее состояние, ссылку на доказательство. Используйте её для описания реального проекта с 5 функциями.

2. **Сравнение строгости верификации**: Выберите 3 функции и спроектируйте как «мягкую» верификацию (например, «в коде нет синтаксических ошибок»), так и «строгую» (например, «сквозной тест проходит»). Сравните частоту ложных срабатываний при каждом подходе.

3. **Аудит принципа единого источника**: Проверьте существующий проект агента на наличие информации о масштабе, противоречащей списку функций (неявные требования в разговорах, TODO-комментарии в коде и т.д.). Разработайте план объединения всей информации в список функций.
