# Лекция 1: Сильные модели не означают надёжного выполнения

Краткое введение: Почему даже лучшие AI-модели терпят неудачу при решении реальных задач? Ответ кроется не в модели, а в окружении, которое её окружает — в harness (шлейфе управления).

## Основная идея

Способности модели и надёжность выполнения — это две разные вещи. Даже самая мощная модель на бенчмарках SWE-bench Verified показывает лишь 50–60% успешных решений. Но это на тщательно отобранных задачах с чёткими описаниями и готовыми тестами. В реальной жизни — с расплывчатыми требованиями, отсутствием тестов и неявными бизнес-правилами — показатель ещё ниже.

**Ключевой принцип:** Когда что-то ломается, сначала проверьте harness, а не меняйте модель.

## Ключевые концепции

### Capability Gap (Разрыв способностей)
Огромная пропасть между производительностью модели на бенчмарках и в реальных задачах. 50–60% на SWE-bench Verified означает, что почти половина реальных проблем остаётся нерешённой.

### Harness (Шлейф управления)
Всё, что находится за пределами модели — инструкции, инструменты, окружение, управление состоянием, обратная связь верификации. Если это не веса модели, это harness.

### Harness-Induced Failure (Ошибка, вызванная harness)
Модель обладает достаточными способностями, но среда выполнения имеет структурные дефекты. Контролируемый эксперимент Anthropic это доказал.

### Verification Gap (Разрыв верификации)
Разрыв между уверенностью агента в своём выводе и фактической корректностью. Агент говорит «я готов», когда на самом деле нет — это наиболее частый режим сбоя.

### Diagnostic Loop (Диагностический цикл)
Выполнить → наблюдать сбой → атрибутировать к конкретному слою harness → исправить этот слой → выполнить заново. Это основная методология harness engineering.

### Definition of Done (Определение «готово»)
Набор условий, которые можно проверить командой — тесты проходят, линт чист, проверка типов проходит. Без явного определения «готово» агент придумает своё.

## Примеры и эксперименты

### Эксперимент «Одна лошадь, разные судьбы» (Anthropic)

Anthropic провёл контролируемый эксперимент. Один и тот же промпт («создай 2D редактор ретро-игр»), одна и та же модель (Opus 4.5), два запуска:

- **Без поддержки:** 20 минут, $9, основные функции игры не работали
- **С полным harness:** 6 часов, $200, игра полностью играбельна

Модель не изменилась. Изменился подход.

### Эксперимент «Миллион строк» (OpenAI, 2025)

Три инженера OpenAI провели эксперимент: они не писали код сами — только Codex. Начав с пустого git-репозитория, через пять месяцев он содержал около миллиона строк кода. Инженеры открыли 1500 PR в среднем по 3,5 на человека в день.

Ранний прогресс был удивительно медленным. Codex был не плох — ему просто не хватало инструментов и структур для достижения высокоуровневых целей. Инженеры постепенно нашли паттерн: разбивать большие цели на маленькие строительные блоки.

### Реальный пример: API-эндпоинты

Команда использовала Claude Sonnet для добавления API-эндпоинтов в Python-приложение (~15 000 строк кода).

**Без harness:** Агент потратил 40% контекстного окна на изучение структуры репозитория, написал код с ошибками и объявил о завершении при нерабочих эндпоинтах.

**С harness (AGENTS.md + команды верификации):** Та же модель успешно выполнила три независимых запуска с ~60% лучшей эффективностью контекста.

## Выводы

1. Способности модели и надёжность выполнения — разные вещи. Даже скаковой конь нуждается в хорошей сбруе.
2. Когда что-то ломается, сначала проверьте harness, потом модель. Смена модели — самый дорогой вариант, и чаще всего проблема не в модели.
3. Каждый сбой — сигнал: ваш harness имеет структурный дефект. Найдите и исправьте его.
4. Не говорите просто «модель недостаточно хороша». Пройдите по пяти слоям: задача нечётко определена, недостаточно контекста, неправильно настроено окружение, отсутствует верификация, потеря состояния между сессиями.
5. Один файл AGENTS.md может быть эффективнее перехода на более дорогую модель.

## Упражнения

### 1. Сравнительный эксперимент
Выберите хорошо знакомую кодовую базу и нетривиальную задачу модификации. Сначала запустите агента (agent) без поддержки harness и запишите сбои. Затем добавьте AGENTS.md и явные команды верификации, запустите того же агента again. Сравните результаты, атрибутируя каждый сбой к одному из пяти защитных слоёв.

### 2. Измерение разрыва верификации
Выберите 5 задач кодирования. После каждой запишите, объявил ли агент о завершении, затем проверьте фактическую корректность независимыми тестами. Вычислите долю случаев, когда агент объявил «готово», а на самом деле нет — это ваш разрыв верификации (verification gap). Подумайте: какие команды верификации уменьшат эту долю?

### 3. Практика диагностического цикла
Найдите задачу, в которой агент repeatedly fails в вашем проекте. Запустите один раз, запишите сбой. Атрибутируйте его к одному из слоёв. Исправьте этот слой. Запустите снова. Повторите 3–5 раундов, записывая улучшения.
