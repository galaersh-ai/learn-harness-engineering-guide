# Лекция 2: Что такое Harness на самом деле

Краткое введение: Слово «harness» часто используется в кругах AI-кодирования, но большинство подразумевают под ним просто файл промптов. Файл промптов — это не harness. Эта лекция даёт точное, применимое на практике определение.

## Основная идея

Harness состоит из пяти подсистем: **инструкции**, **инструменты**, **окружение**, **состояние** и **обратная связь**. Каждая подсистема имеет чёткие обязанности и критерии оценки. Если хотя бы одна подсистема отсутствует, harness неполон, и агент будет работать неуклюже.

## Ключевые концепции

### Пять подсистем Harness

1. **Подсистема инструкций** — AGENTS.md (или CLAUDE.md) с обзором проекта, стеком технологий, командами запуска, жёсткими ограничениями и ссылками на подробную документацию.

2. **Подсистема инструментов** — Достаточный доступ агента к инструментам. Не отключайте shell «из соображений безопасности», но и не открывайте всё — следуйте принципу минимальных привилегий.

3. **Подсистема окружения** — Самоописываемое состояние среды. Используйте `pyproject.toml` или `package.json` для фиксации зависимостей, `.nvmrc` или `.python-version` для указания версий, Docker для воспроизводимости.

4. **Подсистема состояния** — Отслеживание прогресса для длительных задач. Файл `PROGRESS.md` записывает: что сделано, что в процессе, что заблокировано.

5. **Подсистема обратной связи** — Самая высокая отдача. Явно перечислите команды верификации в AGENTS.md.

### Repo as Spec (Репозиторий как спецификация)
Всё необходимое контекстное содержание должно находиться в репозитории, доставляться через структурированные файлы инструкций, явные команды верификации и чёткую организацию каталогов.

### Map, Not Manual (Карта, а не руководство)
AGENTS.md должен быть страницей-оглавлением, а не энциклопедией. Около 100 строк достаточно. Если не влезает — разбейте на директорию `docs/`.

### Constrain, Don't Micromanage (Ограничивайте, а не микроменеджьте)
Хороший harness использует исполняемые правила для ограничения агента, а не перечисляет инструкции одну за другой.

### Remove One at a Time (Удаляйте по одному)
Чтобы количественно оценить вклад каждого компонента harness, удаляйте их по одному и наблюдайте, какое удаление вызывает наибольшее падение производительности.

## Примеры и эксперименты

### Аналогия: новый инженер без документации

Представьте, что вы — новый инженер, попавший в проект без документации. Нет README, нет комментариев в коде, никто не говорит, как запустить тесты. Вы можете писать хороший код — но потратите огромное время на «разобраться в проекте» вместо «решения проблемы».

AI-агент (agent) оказывается в том же положении, и ему ещё хуже. Вы хотя бы можете спросить коллегу. Агент видит только файлы, которые вы ему дали, и команды, которые он может выполнить.

### Инструменты, которые вы уже знаете

- **Claude Code** — читает `CLAUDE.md`, выполняет shell-команды, поддерживает историю сессий. Но если не сказать ему, как запускать тесты, он не сможет проверить свою работу.
- **Cursor** — `.cursorrules` как источник инструкций, терминал как инструмент. Слабое управление состоянием — закройте IDE, и контекст потерян.
- **Codex** — использует git worktrees для изоляции среды выполнения. Работает значительно лучше в репозиториях с `AGENTS.md`.
- **AutoGPT** — предостерегающий пример. Отсутствие структурированного управления состоянием приводит к бесконечному накоплению контекста и зацикливанию.

### История одной команды

Команда использовала GPT-4o для разработки TypeScript + React приложения (~20 000 строк). Четыре этапа добавления компонентов harness:

| Этап | Что добавлено | Успешность |
|------|---------------|------------|
| 1 | Только README | 20% |
| 2 | + AGENTS.md (стек, конвенции) | 60% |
| 3 | + Команды верификации | 80% |
| 4 | + Файл прогресса | 80–100% |

Четыре итерации, модель не изменилась, успешность выросла с 20% до почти 100%.

### Код: команды верификации в AGENTS.md

```markdown
Команды верификации:
- Тесты: pytest tests/ -x
- Проверка типов: mypy src/ --strict
- Линт: ruff check src/
- Полная проверка: make check (включает всё выше)
```

## Выводы

1. **Harness = Инструкции + Инструменты + Окружение + Состояние + Обратная связь.** Все пять подсистем обязательны.
2. Если это не веса модели — это harness. Ваш harness определяет, какая часть способностей модели реально реализуется.
3. Среди пяти подсистем **подсистема обратной связи** обычно даёт наименьшие затраты и наибольшую отдачу. Начните с команд верификации.
4. Используйте «контролируемый тест исключения переменных» для количественной оценки вклада каждой подсистемы.
5. Harness гниёт так же, как код. Регулярно проводите аудит и погашайте «долг harness» так же, как технический долг.

## Упражнения

### 1. Аудит пятерки harness
Возьмите проект, где вы используете AI-агента, и проведите полный аудит по пяти подсистемам. Оцените каждую по шкале 1–5. Найдите подсистему с наименьшей оценкой, потратьте 30 минут на её улучшение и наблюдайте изменение производительности агента.

### 2. Контролируемый тест исключения переменных
Выберите одну модель и одну сложную задачу. Последовательно удаляйте инструкции (удалите AGENTS.md), удаляйте обратную связь (не давайте команды верификации), удаляйте состояние (без файлов прогресса) — удаляя только одно за раз и измеряя падение производительности. Используйте результаты для ранжирования маржинальной ценности каждой подсистемы.

### 3. Анализ affordance (возможностей)
Найдите сценарий в вашем проекте, где агент «хочет сделать что-то, но не может». Определите: это Gulf of Execution (не знает, как действовать) или Gulf of Evaluation (не знает, правильно ли сделал). Затем спроектируйте улучшение harness для преодоления разрыва.
