# Лекция 12: Почему наблюдаемость должна быть внутри харнеса

## Введение

Вы просите агента реализовать функцию. Он работает 20 минут, касается кучи файлов, затем говорит «готово, но два теста не проходят». Вы спрашиваете почему — «не уверен, возможно проблема с таймингом». Вы спрашиваете, какие критические пути он изменил — «дайте посмотрю на код...»

Этот сценарий слишком распространен, и корневая причина — не в способностях агента, а в отсутствии наблюдаемости харнеса. Когда агент выполняет задачу без видимости фактического состояния среды выполнения, каждое его решение — по сути догадка.

**Без наблюдаемости агенты принимают решения в условиях неопределённости, оценки становятся субъективными суждениями, а повторные попытки — слупым блужданием.** И OpenAI, и Anthropic формулируют надёжность как проблему доказательств: харнес должен предоставлять поведение среды выполнения и сигналы оценки в форме, которая может фактически направлять следующее решение.

## Основная идея

Когда харнес лишён наблюдаемости, систематически появляются четыре категории проблем:

- **Невозможно отличить «правильное» от «выглядит правильным»**: Функция выглядит совершенно правильной в код-ревью — правильный синтаксис, здравая логика. Но при выполнении ошибка в обработке граничных условий produces неправильные результаты при определённых входах. Только трассировки среды выполнения могут показать, что фактический путь выполнения отклонился от ожиданий.

- **Оценка становится мистикой**: Без критериев оценки и критериев приёмки оценщикам (человеку или агенту) приходится полагаться на неявные предположения. Один и тот же выход может получить совершенно разные оценки от разных оценщиков.

- **Повторные попытки становятся слепыми догадками**: Когда агент не знает, почему что-то не удалось, направление повторной попытки случайное. Он может долбиться в неправильном направлении — исправляя несвязанные пути кода и игнорируя реальную корневую причину.

- **Обрыв информации при передаче сессии**: Когда незавершённая работа передаётся следующей сессии, отсутствие наблюдаемости означает, что новая сессия должна диагностировать состояние системы с нуля. Наблюдения Anthropic за долгоживущими агентами показывают, что эта избыточная диагностика может съедать 30-50% общего времени сессии.

## Ключевые концепции

- **Наблюдаемость среды выполнения**: Системные сигналы — логи, трассировки, события процессов, проверки работоспособности. Отвечает на вопрос «что сделала система».

- **Наблюдаемость процесса**: Видимость артефактов решений харнеса — планы, критерии оценки, критерии приёмки. Отвечает на вопрос «почему это изменение должно быть принято».

- **Трассировка пути решения**: Полная запись пути решения от начала задачи до завершения, аналогичная трассировке запросов в распределённых системах. Каждый шаг агента вместе с его контекстом записывается — поэтому, когда что-то идёт не так, можно воспроизвести весь процесс.

- **Спринт-контракт**: Краткосрочное соглашение, согласованное перед началом кодирования, определяющее масштаб задачи, стандарты верификации и исключения. Основной инструмент наблюдаемости процесса.

- **Критерии оценки**: Преобразуют оценку качества из субъективного суждения в основанное на доказательствах структурированное оценивание, позволяя разным оценщикам приходить к похожим выводам для одного и того же выхода.

- **Двухслойная наблюдаемость**: Наблюдаемость системного и процессного слоёв, спроектированная одновременно и усиливающая друг друга. Сигналы среды выполнения объясняют поведение; артефакты процесса объясняют намерение.

## Примеры

### Реальный сценарий Claude Code

Рассмотрим харнес с рабочим процессом «планировщик-генератор-оценщик», выполняющий задачу «добавить тёмную тему в приложение».

**Без наблюдаемости**: Планировщик выводит расплывчатое описание. Генератор реализует тёмную тему на основе этой расплывчатости, но результат не соответствует неявным ожиданиям планировщика. Оценщик отклоняет его на основе собственных неявных стандартов, но не может сформулировать, что конкретно не так — просто «не feels right». Генератор повторяет попытку вслепую на расплывчатых причинах отклонения. Цикл повторяется 3-4 раза, занимая около 45 минут, и едва produces приемлемый результат.

**С полной наблюдаемостью**: Планировщик выводит спринт-контракт с перечнем компонентов для модификации, стандартами верификации для каждого и исключениями (например, без стилей для печати). Генератор реализует по контракту, а наблюдаемость среды выполнения записывает процесс загрузки и применения стилей каждого компонента. Оценщик использует критерии оценки для оценки по измерениям, citing конкретные доказательства: «Контраст цвета кнопки недостаточен (стандарт WCAG AA 4.5:1, измерено 2.1:1)». Одна итерация produces высококачественный результат, примерно за 15 минут.

**3x разница в эффективности. Единственная переменная — наблюдаемость.**

### Эксперимент Anthropic с трёхагентной архитектурой

В марте 2026 года Anthropic опубликовал систематический эксперимент с харнесом. Они запускали одну и ту же задачу («создать браузерный DAW с использованием Web Audio API») с тремя разными архитектурами и записывали подробные данные по фазам:

| Агент и фаза | Длительность | Стоимость |
|---|---|---|
| Планировщик | 4.7 мин | $0.46 |
| Сборка, раунд 1 | 2 ч 7 мин | $71.08 |
| QA, раунд 1 | 8.8 мин | $3.24 |
| Сборка, раунд 2 | 1 ч 2 мин | $36.89 |
| QA, раунд 2 | 6.8 мин | $3.09 |
| Сборка, раунд 3 | 10.9 мин | $5.88 |
| QA, раунд 3 | 9.6 мин | $4.06 |
| **Итого** | **3 ч 50 мин** | **$124.70** |

Каждый из трёх агентов имел чёткую роль, и каждый играл ясную роль в наблюдаемости:

- **Планировщик**: Получает требование пользователя в 1-4 предложения и расширяет его в полную спецификацию продукта.
- **Генератор**: Реализует функцию за функцией, спринт за спринтом. Перед каждым спринтом согласовывает спринт-контракт с оценщиком.
- **Оценщик**: Использует Playwright MCP для взаимодействия с запущенным приложением как реальный пользователь. Оценивает каждый спринт по четырём измерениям: глубина продукта, функциональность, визуальный дизайн и качество кода.

### Пример спринт-контракта

```markdown
# Sprint Contract: Dark Mode Support

## Scope
- Modify the theme toggle component
- Update global CSS variables
- Add dark mode tests

## Verification Standards
- Visual regression tests pass for each component
- Main flow end-to-end tests pass
- No flash of unstyled content (FOUC)

## Exclusions
- Not handling print styles
- Not handling third-party component dark mode
```

## Выводы

- **Наблюдаемость — не функция, добавляемая постфактум** — это ключевая возможность, которая должна быть заложена с самого начала.
- **Двухслойная наблюдаемость**: сигналы среды выполнения объясняют «что произошло», артефакты процесса объясняют «почему это было сделано так».
- **Спринт-контракты** предотвращают ситуацию, когда генератор строит то, что оценщик немедленно отклоняет по предсказуемым причинам.
- **Критерии оценки** обеспечивают воспроизводимость — разные оценщики produces похожие оценки для одного и того же выхода.
- **Трассировка пути решения** позволяет воспроизвести весь процесс, когда что-то идёт не так.

## Упражнения

1. **Аудит наблюдаемости**: Проведите аудит вашего текущего харнеса на наблюдаемость системного и процессного слоёв. Найдите состояния системы, которые невозможно отличить по существующим сигналам, и предложите дополнения.

2. **Спринт-контракт на практике**: Напишите спринт-контракт для реальной задачи. Позвольте агенту выполнять по контракту и сравните эффективность и качество с контрактом и без него.

3. **Трассировка задачи**: Запишите каждый шаг агента во время полной задачи кодирования. Аннотируйте с использованием семантических конвенций OpenTelemetry. Проанализируйте трассировку на наличие информационных узких мест — каким шагам не хватает достаточной поддержки сигналами для их решений.
