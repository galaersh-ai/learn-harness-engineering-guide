# Лекция 11: Почему сквозное тестирование меняет результаты

## Введение

Вы просите агента добавить функцию экспорта файлов в Electron-приложение. Он пишет компонент рендерера, скрипт предзагрузки и логику сервисного слоя. Модульные тесты для каждого компонента проходят. Агент говорит «готово». Вы фактически нажимаете кнопку экспорта — формат пути к файлу неправильный, индикатор прогресса не реагирует, а экспорт больших файлов вызывает утечку памяти. Пять дефектов на границах компонентов, а модульные тесты не поймали ни одного.

Каждая часть по отдельности выглядит «правильной», но проблемы проявляются в момент их соединения. Пирамида тестирования Google говорит нам, что большая база модульных тестов необходима, но остановка на них означает, что вы систематически будете пропускать проблемы взаимодействия компонентов. Для ИИ-агентов кодирования эта проблема ещё хуже, потому что агенты tend to запускать только самые быстрые тесты, а затем объявлять о завершении. **Только сквозное тестирование может доказать отсутствие системных дефектов.**

## Основная идея

Дизайн-философия модульного тестирования — изоляция: мокирование зависимостей, фокус на тестируемом блоке. Эта философия делает модульные тесты быстрыми и точными, но также создаёт систематические слепые зоны. Каждый модуль работает идеально в изоляции, однако следующие категории проблем проявляются только когда всё фактически запускается вместе.

## Ключевые концепции

- **Слепые зоны модульных тестов**: Их дизайн изоляции — именно то, что мешает обнаруживать проблемы взаимодействия.

- **Несовпадение интерфейсов**: Рендерер передаёт скрипту предзагрузки относительный путь к файлу, но скрипт предзагрузки ожидает абсолютный путь. Их соответствующие модульные тесты оба используют моки и оба проходят. Проблема обнаруживается только при сквозном тестировании.

- **Ошибки распространения состояния**: Миграция базы данных изменяет схему таблицы, но кэширующий слой ORM всё ещё хранит записи кэша со старой схемой. Модульные тесты поднимают новую моковую среду каждый раз, поэтому никогда не выявляют такую межуровневую несогласованность состояний.

- **Проблемы жизненного цикла ресурсов**: Приобретение и освобождение файловых дескрипторов, подключений к базе данных и сетевых сокетов охватывают несколько компонентов. Модульные тесты создают и уничтожают независимые ресурсы для каждого тестового случая, поэтому никогда не выявляют конкуренцию за ресурсы или утечки.

- **Зависимость от среды**: Код ведёт себя правильно в тестовой среде (где всё замокировано), но отказывается в реальной среде из-за различий в конфигурации, сетевой задержки или недоступности сервиса.

- **Иерархия обнаружения дефектов**: Дефекты, обнаруживаемые модульными тестами <= дефекты, обнаруживаемые интеграционными тестами <= дефекты, обнаруживаемые сквозными тестами. Способность обнаружения увеличивается с каждым слоем.

- **Автоматизация архитектурных ограничений**: Превращение правил из архитектурных документов (например, «процесс рендерера не должен напрямую обращаться к файловой системе») в исполняемые, автоматизированные проверки — переход от «написано на бумаге» до «запускается в CI».

- **Повышение отзывов о ревью**: Превращение повторяющихся комментариев код-ревью в автоматизированные тесты. Каждый раз, когда обнаруживается новая категория повторяющейся проблемы, добавляется правило, и харнес автоматически становится сильнее.

- **Действенные сообщения об ошибках**: Сообщения о сбоях должны не просто указывать «что пошло не так», но и точно говорить агенту, как это исправлять, превращая сбои тестов в самокорректирующиеся циклы обратной связи.

## Примеры

### Сквозное тестирование не только меняет результаты — оно меняет поведение

Когда агент знает, что его работа будет проверена сквозными тестами, его поведение при написании кода меняется:

1. **Мысли о границах**: При написании кода он начинает спрашивать «как этот интерфейс соединяется с вышестоящим?» вместо фокуса на одной функции изолированно.
2. **Соблюдение ограничений**: В системах с архитектурными ограничениями сквозные тесты заставляют агента соблюдать правила границ.
3. **Упреждающая обработка ошибок**: Сквозные тесты обычно включают сценарии сбоев, что подталкивает агента к размышлению об обработке исключений.

### Реальный случай

**Задача**: Реализовать функцию экспорта файлов в Electron-приложении. Включает UI процесса рендерера, прокси файловой системы скрипта предзагрузки и трансформацию данных сервисного слоя.

**Фаза модульных тестов**: Тесты компонента рендерера (пройдены, файловые операции замокированы), тесты скрипта предзагрузки (пройдены, файловая система замокирована), тесты сервисного слоя (пройдены, источник данных замокирован). Агент объявляет о завершении.

**Дефекты, выявленные сквозными тестами**:

| Дефект | Описание | Модульный тест | E2E |
|---|---|---|---|
| Несовпадение интерфейсов | Несогласованный формат пути к файлу | Пропущен | Пойман |
| Распространение состояния | Прогресс экспорта не отправлен обратно в UI через IPC | Пропущен | Пойман |
| Утечка ресурсов | Дескрипторы экспорта больших файлов не освобождены | Пропущен | Пойман |
| Проблема с разрешениями | Разные разрешения в упакованной среде | Пропущен | Пойман |
| Распространение ошибок | Исключения сервисного слоя не достигли UI-слоя | Пропущен | Пойман |

Все 5 дефектов были пойманы сквозными тестами; модульные тесты не поймали ни одного. Компромисс — увеличение времени тестирования с 2 секунд до 15 секунд — вполне приемлемо в рабочем процессе агента.

### Пример действенного сообщения об ошибке

```
ERROR: Found direct import of 'fs' in src/renderer/App.tsx:12
WHY: Renderer process has no access to Node.js APIs for security
FIX: Move file operations to src/preload/file-ops.ts and call via window.api.readFile()
```

```

```

## Выводы

- **Слепые зоны модульных тестов** — их дизайн изоляции именно то, что мешает обнаруживать проблемы взаимодействия.
- **Сквозное тестирование меняет поведение** — оно сдвигает фокус к интеграции и границам.
- **Автоматизация архитектурных ограничений** — они не написаны в документе, ждущем прочтения, а автоматически проверяются при каждом коммите.
- **Действенные сообщения об ошибках** — включают конкретные шаги «как исправить», формируя самокорректирующийся цикл обратной связи.
- **Повышение отзывов о ревью** — каждая пойманная категория дефектов становится постоянной линией обороны.

## Упражнения

1. **Сквозной анализ дефектов**: Выберите задачу модификации, затрагивающую не менее трёх компонентов. Сначала запустите только модульные тесты и запишите результаты, затем запустите сквозные тесты. Проанализируйте каждый дополнительно обнаруженный дефект и классифицируйте, какой тип межуровневой проблемы взаимодействия он представляет.

2. **Автоматизация архитектурного ограничения**: Выберите архитектурное ограничение из вашего проекта и превратите его в исполняемую проверку (с действенным сообщением об ошибке для агента). Интегрируйте его в харнес и проверьте эффективность с помощью базовой задачи.

3. **Повышение типа комментария из ревью**: Найдите повторяющийся тип комментария из истории код-ревью и преобразуйте его в автоматизированную проверку по пятишаговому процессу. Сравните частоту этой категории проблем до и после повышения.
