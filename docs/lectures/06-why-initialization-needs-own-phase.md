# Лекция 6: Почему инициализации нужна своя фаза

Краткое введение: Вы начинаете новую сессию агента и говорите «добавить функцию поиска». Он сразу начинает кодировать — похвальный энтузиазм. Через 20 минут обнаруживает, что тестовый фреймворк настроен неправильно, тратит ещё 10 минут на исправление, затем находит проблемы с миграцией БД. Функция поиска добавлена, но сессия была неэффективной.

## Основная идея

Инициализация и реализация — два фундаментально разных типа работы с разными целями оптимизации. Смешивание их только снижает эффективность обоих. Инициализация должна быть выделенной фазой, а не смешиваться с реализацией.

## Ключевые концепции

### Initialization Phase (Фаза инициализации)
Первая фаза в жизненном цикле агента — она только устанавливает предпосылки для последующей реализации, без разработки функций. Её выход — инфраструктура, а не бизнес-код.

### Startup Readiness Checklist (Контрольный список готовности к запуску)
Условия, при которых проект может быть однозначно эксплуатирован свежей сессией агента: может запуститься, может тестировать, может видеть прогресс, может продолжить. Четыре условия, все обязательны.

### From Scratch vs From Template (С нуля vs из шаблона)
Начало с нуля означает, что агент должен самостоятельно вывести структуру проекта из пустой директории. Начало из шаблона означает, что инфраструктура уже на месте. Начало из шаблона значительно превосходит начало с нуля.

### Always Ready to Hand Off (Всегда готов к передаче)
Проект в любой момент находится в состоянии, где свежий агент может подхватить работу. Никаких устных объяснений — достаточно взглянуть на содержимое репозитория.

### Time from Start to First Passing Test (Время от старта до первого прохождения теста)
Время от начала проекта до прохождения верификации первой функции. Основная метрика эффективности инициализации.

### Success Rate of Subsequent Sessions (Успешность последующих сессий)
Доля последующих сессий, которые могут успешно выполнять задачи без依赖 от неявных знаний. Лучшая мера качества инициализации.

## Примеры и эксперименты

### Два фундаментально разных типа работы

Инициализация и реализация имеют совершенно разные цели оптимизации:
- **Фаза реализации** — максимизировать количество и качество верифицированных функций
- **Фаза инициализации** — максимизировать надёжность и эффективность всей последующей реализации

При смешивании агент сталкивается с задачей многокритериальной оптимизации: одновременно строить инфраструктуру и писать функциональный код. Без явной установки приоритетов агент естественно тяготеет к написанию кода (потому что это непосредственно видимый результат), жертвуя инфраструктурой (её ценность проявляется только в последующих сессиях).

### Что происходит при смешивании

**Инфраструктура не строится основательно.** Агент тратит 80% усилий на функциональный код и оставшиеся 20% — на «createForm» инфраструктуры. Тестовый фреймворк настроен, но не проверен. Правила линта установлены, но слишком мягкие. Файл прогресса не создан.

**Накопление непроверенного кода.** Функциональный код, написанный до правильной настройки тестового фреймворка — когда вы наконец вернётесь добавить тесты, можете обнаружить, что сам дизайн был flawed.

**Трата бюджета контекста.** Работа по инициализации потребляет значительную часть бюджета, оставляя меньше для реализации функций. Результат: первая сессия выполняет только половину функций.

**Мины неявных предположений.** Решения, которые агент принимает при инициализации (какой тестовый фреймворк, как организовать директории) — если не записаны явно, последующие сессии могут сделать противоречивый выбор. Первая сессия выбрала Vitest, вторая не знает и вводит Jest.

### Данные Anthropic

Проекты с выделенной фазой инициализации показали на 31% более высокую долю выполнения функций в многосессионных сценариях по сравнению со смешанным подходом. Время, вложенное в фазу инициализации, полностью окупается в следующих 3–4 сессиях.

### Реальный пример: React-проект

**Смешанный подход:** Агент одновременно создал каркас проекта и реализовал первую функцию в сессии 1. В конце сессии репозиторий содержал рабочий код, но без явной документации команд запуска/тестирования, без файла отслеживания прогресса, без разбиения задач. Сессия 2 потратила ~20 минут на вывод структуры проекта.

**Выделенная инициализация:** Сессия 1 — только инициализация: создание структуры из шаблона, настройка тестового фреймворка, написание и проверка одного примера теста, создание контрольного списка и разбиения задач, коммит начального чекпоинта. Время пересборки сессии 2 — менее 3 минут.

**Сравнение полного цикла:** общее время пересборки смешанного подхода (по всем сессиям) было примерно на 60% больше выделенного. Дополнительные 20 минут, потраченные на инициализацию, окупились многократно.

### Код: контрольный список готовности к запуску

```markdown
# Контрольный список готовности к запуску

## Команды запуска
- Установка зависимостей: `make setup`
- Запуск dev-сервера: `make dev`
- Запуск тестов: `make test`
- Полная проверка: `make check`

## Текущее состояние
- Все зависимости установлены и зафиксированы
- Тестовый фреймворк настроен (Vitest + React Testing Library)
- Пример теста проходит (1/1)
- Правила линта настроены (ESLint + Prettier)

## Структура проекта
- src/ — Исходный код
- src/components/ — React-компоненты
- src/api/ — API-клиент
- tests/ — Тестовые файлы
```

### Код: разбиение задач

```markdown
# Разбиение задач

## Задача 1: Базы аутентификации пользователей
- Реализовать JWT auth-middleware
- Добавить эндпоинты login/register
- Критерий приёмки: pytest tests/test_auth.py все проходят

## Задача 2: Страница профиля пользователя
- Реализовать CRUD профиля
- Добавить форму редактирования
- Критерий приёмки: pytest tests/test_profile.py все проходят

## Задача 3: Функция поиска
- ...
```

### Код: контрольный список приёмки инициализации

```markdown
## Контрольный список приёмки инициализации
- [ ] `make setup` проходит с нуля
- [ ] `make test` имеет хотя бы один проходящий тест
- [ ] Новая сессия агента может ответить «как запустить» и «как тестировать» только из содержимого репозитория
- [ ] Файл разбиения задач существует с минимум 3 задачами
- [ ] Всё закоммичено в git
```

## Выводы

1. Инициализация и реализация имеют разные цели оптимизации — смешивание снижает эффективность обоих.
2. Выход инициализации — не бизнес-код, а инфраструктура: рабочее окружение, верифицируемые тесты, контрольный список готовности, разбиение задач.
3. Валидируйте инициализацию четырьмя условиями контрольного списка: может запуститься, может тестировать, может видеть прогресс, может продолжить.
4. Начало из шаблона превосходит начало с нуля. Используйте шаблоны проектов для предустановки стандартизированной инфраструктуры.
5. Время, вложенное в инициализацию, полностью окупается в следующих 3–4 сессиях. Это не дополнительные затраты — это предварительная инвестиция.

## Упражнения

### 1. Дизайн контрольного списка готовности
Напишите полный контрольный список готовности к запуску для вашего проекта. Затем откройте совершенно свежую сессию агента, покажите только содержимое репозитория (без вербального контекста) и попробуйте запустить проект, запустить тесты и понять текущий прогресс. Запишите каждую проблему — каждая соответствует отсутствующему пункту контрольного списка.

### 2. Сравнительный эксперимент
Выберите moderately сложный новый проект. Подход A: агент инициализируется и делает первую реализацию одновременно. Подход B: одна сессия на выделенную инициализацию, реализация начинается в сессии 2. После 4 сессий сравните время от старта до первого прохождения теста, стоимость пересборки и долю выполнения функций.

### 3. Контрольный список приёмки инициализации
Спроектируйте контрольный список приёмки инициализации для вашего проекта. Позвольте свежей сессии агента выполнить каждый пункт и запишите, какие проходят, какие нет. Пункты, которые не проходят — это места, где ваш harness нужно усиливать.
