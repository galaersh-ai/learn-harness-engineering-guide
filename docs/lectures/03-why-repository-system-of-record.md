# Лекция 3: Репозиторий как единый источник истины

Краткое введение: Решения вашей команды по архитектуре разбросаны по Confluence, Slack, Jira и головам нескольких старших инженеров. Для людей это еле-еле работает. Для AI-агента информация, которой нет в репозитории, просто не существует.

## Основная идея

Агент имеет только три источника входных данных: системные промпты и описания задач, содержимое файлов репозитория и вывод выполнения инструментов. Ваши переписки в Slack, тикеты Jira, страницы Confluence — агент не видит ничего из этого. Он не может «спросить кого-то» или «поискать в чатах». Весь его рабочий мир — это репозиторий.

**Вопрос:** дадите ли вы ему достаточно хорошую карту?

## Ключевые концепции

### Knowledge Visibility Gap (Разрыв видимости знаний)
Доля общих знаний о проекте, которая НЕ находится в репозитории. Чем больше разрыв, тем выше частота сбоев агента.

### System of Record (Система записи)
Репозиторий кода как авторитетный источник решений по проекту, архитектурных ограничений, состояния выполнения и стандартов верификации. Репозиторий имеет последнее слово — больше нигде не считается.

### Fresh Session Test (Тест свежей сессии)
Откройте совершенно новую сессию агента, дайте ей только содержимое репозитория и проверьте, может ли она ответить на пять базовых вопросов:
1. Что это за система?
2. Как она организована?
3. Как её запустить?
4. Как её верифицировать?
5. Какой текущий прогресс?

### Discovery Cost (Стоимость обнаружения)
Сколько бюджета контекста (context window) сжигает агент для нахождения одного ключего фрагмента информации. Критическая информация должна быть размещена там, где агент видит её первой.

### Knowledge Decay Rate (Скорость распада знаний)
Доля записей знаний в репозитории, которые устаревают за единицу времени. Документация, отставшая от кода — злейший враг. Хуже отсутствия документации — устаревшая документация.

### ACID-аналогия
Применение принципов транзакций баз данных к управлению состоянием агента:
- **Atomicity (Атомарность):** Каждая «логическая операция» — один git-коммит. Если прервалось — `git stash` для отката.
- **Consistency (Согласованность):** Определите предикаты проверки «согласованного состояния» — все тесты проходят, линт без ошибок.
- **Isolation (Изоляция):** При параллельной работе нескольких агентов проектируйте файлы состояния для избежания гонок.
- **Durability (Долговечность):** Критические знания проекта живут в git-отслеживаемых файлах.

## Примеры и эксперименты

### Что принадлежит на карте

OpenAI прямо говорит: **информация, которой нет в репозитории, не существует для агента.** Они называют это принципом «repo as spec» — репозиторий сам является спецификацией высшего авторитета.

50-строчный `ARCHITECTURE.md` в директории `src/api/` гораздо полезнее 500-страничного дизайн-документа в Confluence, который никто не поддерживает. Близость важнее длины, потому что информация полезна только тогда, когда она под рукой в момент необходимости.

### Структура репозитория

```
project/
├── AGENTS.md              # Точка входа: обзор, команды, жёсткие ограничения
├── src/
│   ├── api/
│   │   ├── ARCHITECTURE.md  # Архитектурные решения API-слоя
│   │   └── ...
│   ├── db/
│   │   ├── CONSTRAINTS.md   # Жёсткие ограничения работы с БД
│   │   └── ...
│   └── ...
├── PROGRESS.md             # Текущий прогресс: сделано, в процессе, заблокировано
└── Makefile                # Стандартизированные команды: setup, test, lint, check
```

### Реальная история трансформации

Команда поддерживала e-commerce платформу с ~30 микросервисами. Архитектурные решения были разбросаны: Confluence (частично устаревший), Slack (трудно искать), головы старших инженеров (не масштабируется), спорадические комментарии в коде (не систематично).

После внедрения AI-агентов 70% задач требовали вмешательства человека. Почти каждый сбой связан с нарушением агентом неявного ограничения, «которое все знают, но никто не записал».

**После трансформации:**
- Создан `AGENTS.md` в корне репозитория
- Добавлен `ARCHITECTURE.md` в каждой директории микросервиса
- Централизованный `CONSTRAINTS.md` с явным языком «MUST / MUST NOT»
- `PROGRESS.md` в каждой директории сервиса

Тот же агент мог ответить на все ключевые вопросы проекта в свежей сессии.

## Выводы

1. Знания, которых нет в репозитории, не существуют для агента. Помещение критической информации о решениях в репозиторий — самая фундаментальная инвестиция в harness.
2. Используйте «тест свежей сессии» для оценки качества репозитория.
3. Знания должны быть рядом с кодом, минимальными, но полными и обновляться вместе с кодом.
4. Используйте ACID-принципы для состояния агента: атомарные коммиты, верификация согласованности, изоляция конкурентного доступа, долговечность критических знаний.
5. Распад знаний — злейший враг. Устаревшая документация опаснее отсутствия документации.

## Упражнения

### 1. Тест свежей сессии
Откройте совершенно свежую сессию агента в вашем проекте (не давайте никакого вербального контекста), позвольте видеть только содержимое репозитория и задайте пять вопросов. Запишите, на какие не может ответить, затем улучшайте репозиторий до ответа на все.

### 2. Количественная оценка экстернализации знаний
Перечислите все решения и ограничения, важные для разработки в вашем проекте. Отметьте каждый элемент как «внутри» или «вне» репозитория. Вычислите ваш разрыв видимости знаний (доля элементов вне репозитория). Составьте план сокращения разрыва ниже 10%.

### 3. ACID-оценка
Оцените управление состоянием вашего проекта с помощью ACID-аналогии: Атомарность — можно ли чисто откатить операции агента? Согласованность — есть ли в репозитории верификация «согласованного состояния»? Изоляция — не мешают ли друг другу параллельные агенты? Долговечность — все ли межсессионные знания правильно сохранены?
